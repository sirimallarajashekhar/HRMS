## 2026-11-26 – P0.4 Authentication, users, roles and data scopes
**Built:** Authorization: permission catalogue (module.entity.action constants, unknown codes rejected), [RequirePermission], dynamic policies, a deny-by-default fallback, a handler that honours a token only for the tenant it names, and a host-wide scan that fails the build when an endpoint does not declare its authorization. Identity module: user_account, role, role_permission, user_role_scope, tenant_security_policy (effective-dated), permission, user_recovery_code (migrations InitialIdentity, OAuthStores, Mfa); the six approved default roles (tenant_admin, hr_admin and payroll_admin require MFA); lockout state machine, tenant password policy, PBKDF2 hashing at 210,000 iterations. OpenIddict 7.1.0 token server in the API host: password and refresh grants for the apps, client credentials for integrations (each bound to one tenant and a fixed role set), access tokens 10 minutes, refresh tokens rotate and cannot be replayed, rate limited. TOTP MFA (RFC 6238, single-use steps, hashed recovery codes), AES-256-GCM field encryption for the MFA secret, and self-service endpoints under /api/v1/account (enrol, confirm, disable MFA, change password). Data-scope service (a DataScope value, not a list of 20,000 ids) behind an interface the employee module completes in P0.6; masking rules and a view_sensitive check. `bootstrap-tenant` command for the first tenant and administrator. 706 tests (Release), zero warnings.
**Decisions:** OpenIddict pinned to 7.1.0, the last release whose net9.0 asset works with our EF Core 9 pin (7.2+ needs EF Core 10); the net9.0-library and separate-process options were tried or costed and rejected (NU1109 in the net10 host; second runtime, multi-targeting and pin conflicts). The advisories in 7.2-7.9 are covered by configuration, each pinned by a test: authorization-entry and token-entry validation enabled together (GHSA-cxgj-hwwh-855g), no client key sets (GHSA-925x-4h4v-2792), no HTTP client stack (CVE-2026-111497). Password grant as specified, with uniform refusals and equal work for every failure; the authenticated caller tenant comes from the token claim only; no user-management APIs yet (bootstrap command only); MFA-required roles get an enrolment-only session until enrolled.
**Assumptions to confirm (business rules):** default password policy is length 12 with no composition rules, 5 failed attempts then a 15-minute lock; access tokens 10 minutes and refresh tokens 14 days without sliding; the draft role-to-permission grants in DefaultRoles (manager sees legal entities, auditor is read-only, employee has none); lockout and password rules apply per tenant through tenant_security_policy, effective-dated; recovery codes: 8 per enrolment, replaced on re-enrolment; a locked-out or disabled account gets the same refusal as a wrong password (no distinct message).
**Learned:** NuGet re-resolves a transitive package for the consuming project framework, so a net9.0 library cannot shield a net10 host from a package that wants EF Core 10. `AuthorizationMiddleware` builds every registered authorization handler for every request, anonymous ones included, so anything reaching the database must be resolved lazily or a host without a database fails on /ping. DynamicParameters.ParameterNames does not see anonymous-object members. The Identity password hasher throws on a non-Base64 stored hash (now a wrong password). Optimistic retries under a burst of parallel guesses must exceed the burst size or lockout under-counts. A per-IP limit must allow a whole office behind one NAT.
**Follow-ups:**
- High: forwarded headers and trusted proxies. Behind a TLS-terminating proxy OpenIddict sees HTTP and refuses, and per-IP limits see one address. Needed before any real deployment.
- High: password reset and account unlock flows (a locked account has no self-service way back, and lockout is a denial-of-service lever on an admin); security events (sign-in, lockout, MFA changes) belong in the audit log (P0.7).
- Production secrets: signing and encryption certificates, field-encryption keys and the first-party client setup; document rotation. Run migrations (Core, Identity) from a deploy step, then bootstrap-tenant.
- Access tokens are not checked against the account on every request: a disabled user keeps access for up to 10 minutes (refresh is refused at once). Add a stamp check or shorter lifetime if that is too long.
- Permission cache is per process, 60 s: with several API instances a role change reaches each within a minute. Add distributed invalidation if that is too slow.
- Request validation is hand-written in the account endpoints; adopt FluentValidation as the convention says when more endpoints arrive. No Idempotency-Key needed yet (no money or punch endpoints).
- Revisit OpenIddict 7.9.0+ when Pomelo ships EF Core 10. The integration suite now takes about 7 minutes (CI budget 30): trim hashing cost or split the project before it nears the limit.
- Employee module (P0.6) must register IEmployeeScopeExpander (the default only knows Self) and link user_account.employee_id; user and role management APIs arrive with the admin screens (P0.12).

## 2026-11-26 – P0.5 Organisation structure masters
**Built:** Core module CRUD for org_unit_type, org_unit, location, geofence, grade, designation, cost_centre and employee_type under /api/v1 (/org-unit-types, /org-units, /locations, /locations/{id}/geofences, /grades, /designations, /cost-centres, /employee-types), each behind its own core.<master>.view/manage permission (granted to the default roles; the tenant administrator gets all). Codes are upper case and unique per tenant (soft-deleted rows release them); updates carry the rowVersion they were based on (409 when stale); lists are paged (default 50, at most 200) with search and active filters, plus type/parent/asOf on org units, grade on designations and legal entity on cost centres; request bodies are capped at 64 KB. Org units keep an effective-dated parent (org_unit_parent): a move closes the open period the day before and opens the next in one transaction, history is append-only, GET /org-units/{id}/parents lists it, asOf reads any date, GET /org-units/tree returns the whole tree in one query. Rules: a parent sits on a strictly higher level than the unit, the type of a unit is fixed, the level of a type with units cannot change, no cycles (OrgTree checks the start date and every later change date), a parent must exist, be active and belong to the tenant. Geofences are circles (radius 1 to 100,000 m) or one-ring GeoJSON polygons (4 to 501 positions, closed, no self-intersection or fold-back, non-zero area, 32 KB cap), stored as validated, normalised text; GeoPoint value object (six decimals, rounded away from zero). Deletion is a soft delete refused with core.<master>.in_use while Core references remain (children, units of a type, designations of a grade, geofences of a location) or while another module reports use through the new IMasterUsageCheck contract (MasterKinds). One migration (CoreOrgStructure, additive). Verified: 921 tests pass (249 Core unit, 27 architecture, 86 shared kernel, 152 identity, 407 integration of which 122 are new API tests).
**Decisions:** only the org-unit parent is effective-dated (other masters use an active flag, soft delete and later the P0.7 audit log); one generic MasterService for the six coded masters, custom services for org units and geofences; no FluentValidation yet (invariants live in the domain factories, as in P0.3 and P0.4) and no Idempotency-Key (no money or punch endpoints); polygon stored as text, not a MySQL spatial column, because punch checks will test points in-process; rowVersion travels in the body, not If-Match; lists use offset paging with a total (these masters are small).
**Assumptions to confirm (business rules):** a tenant may have several root units; the work week is a Monday-first day mask (alternate-Saturday style rules belong to the policy engine); grades carry a rank but no pay band until payroll defines it; locations are not tied to a legal entity; cost centres are flat; an inactive master stays readable and keeps working where used, new assignments to it are for the employee module to refuse; a unit created with a future start date is not in today's tree and shows no parent until then; the default start date is the UTC date, not the tenant's local date; the playbook's FSD section 4.1 was not available (docs/FSD.md is not in the repo), so field lists and rules come from the playbook text alone.
**Learned:** the ASP.NET route-handler analyzer throws (AD0001) on generic endpoint lambdas, so Hrms.Core.Api suppresses that one id with a comment; EF cannot translate a filter over a constructor-built projection (use member initialisers); Result.Success(null) throws, so nullable results need another shape; a JSON null body binds null into a non-nullable minimal-API parameter and reached the service as a 500, so write handlers take the body as nullable and answer 422 core.request.body_required; the in-memory test server neither enforces the body-size limit nor maps BadHttpRequestException, so the limit is asserted on endpoint metadata and not exercised end to end; sharing one host per test class (class fixture) cut the new API suite from 8 minutes to seconds.

- The integration suite now takes about 10m40s locally (CI budget 30 minutes): trim hashing/host start-up cost or split the project before it nears the limit.
